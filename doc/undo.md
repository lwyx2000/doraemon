## 0. 判断原则

一条能力被判「不能做」，只可能是下面四类原因之一。先归类，再谈补救：

| 类别 | 含义 | 补救难度 |
|---|---|---|
| **A. 私有数据缺失** | 数据只存在于某个不公开的系统（如 woody 的 palmmicro bot） | 要拿到该系统的授权，或重建等价的数值方法 |
| **B. 资产类别/交易所源缺失** | 公开市场有，但 doraemon 现在没有对应行情源 | 接源即可，成本可估 |
| **C. 历史高频数据缺失** | 公开源只有日频，拿不到历史 tick／分时 | 买历史数据，或从今天开始自己积累 |
| **D. 不值得做** | 数据能拿到，但成本远大于收益 | 明确放弃，写进本文防止反复讨论 |

**一条铁律**（继承 lofarb）：
> **宁可显示 `-`，不可用近似值冒充精确值。**
> 如果能做但只能做到「近似」，必须在配置里打 `*_is_proxy: true` 并在 UI 标注，
> 且**不得接入套利信号计算**。

## §A · 魔法公式（hedge 常量折叠）— 类别 A，不做

### A.1 它是什么

lofarb 的 `unified_valuation.basket_valuation` 有两个分支。
当「单成分 + `hedge > 0`」时走魔法公式（代码 L47-52）：

```python
if hedge is not None and hedge > 0 and len(components) == 1:
    c = components[0]; cp = c.get('current_price', 0) or 0
    if cp > 0 and fx_now is not None and fx_now > 0:
        return base_nav * (1.0 - position) + (cp * fx_now) / hedge
```

等价形式（矩阵公式代数展开，`hedge = calibration / position`）：

```
est_nav = nav × (1 − pos) + P_now × fx_now / hedge
```

### A.2 它解决什么问题

**问题**：如果基金持有 100% 单一 ETF，矩阵公式要求知道 `P_base`（净值基准日的底层收盘价）。
但在跨时区、跨市场时，`P_base` 到底该取哪一天的收盘很难定准，
取错一天就会让整个估值偏移。

**hedge 的巧妙处**：它是一个「标的价格 → 基金净值」的**折算系数**，
由 woody 用期现回归算出来，直接绕过了「基准日选择」这个麻烦。
只要知道当前价和 hedge，就能反推净值。

lofarb 里 `hedge_allowed()` 明确只允许 `''`（未标注）和 `etf` 两种方法用它；
`basket`、`index`、`equity_asia` 一律 `static_hedge: False`。
原因是有血的教训：

> 161125（标普500）用 hedge 后估算差 **10 倍**；
> 161130（纳指LOF）差 **41 倍**。
> 因为这两个基金的标的是 `.INX`/`.NDX` 指数，而 woody 的 hedge 是按 SPY/QQQ 的 ETF 价格算的，
> 指数点位（约 5800）和 ETF 价格（约 580）差了整整一个数量级。

### A.3 为什么 doraemon 做不了

**不是算法问题，是数据不存在。**

| 需要的东西 | lofarb 里有吗 | lofarb 从哪来 | doraemon 有吗 |
|---|---|---|---|
| `hedge`（折算系数） | ✅ | `fund_daily_factors.hedge` | ❌ 表都不存在 |
| `calibration`（期现校准） | ✅ | `fund_daily_factors.calibration`、`futures_daily.calibration` | ❌ |
| `position`（仓位） | ✅ | `fund_daily_factors.position` | ✅ 有（配置静态值） |

`hedge` 与 `calibration` 的写入方只有一处：
`arbcore/fetchers/woody_api_service.py` → `db.upsert_fund_factor(..., calibration=cal, hedge=hed, ...)`。
数据源头是 palmmicro 的 bot 接口（需要 `WOODY_USERNAME` / `WOODY_PASSWORD`）。

### A.4 要什么数据才能做

| 字段 | 含义 | 量纲 | 频率 | 覆盖 | 获取途径 | 可行性 |
|---|---|---|---|---|---|---|
| `hedge` | 每单位底层标的价格贡献折算为基金净值的系数 | 标的价格 / 净值（例：GLD 的 hedge≈10.97） | 日 | 每只基金 × 每成分 | ① palmmicro bot（woody）<br>② 自己用期现回归反推 | ① 要账号<br>② 可试，但不稳定 |
| `calibration` | 期货价 → 现货等价价的折算率 | 期货价 / 现货价（无量纲，约 1.0x） | 日 | 每个期货合约 | ① woody<br>② `calibration = futures_price / spot_price` 自算 | ② 可行，需同时有期货与现货价 |

**「自己反推 hedge」的做法与局限**：

```
hedge = calibration / position
calibration = Σ wᵢ × Pᵢ_base × fx_base / nav
```

要反推必须同时知道：连续多日的 `nav`、`position`、`P_base`、`fx`。
再对 `nav` 做最小二乘拟合求系数。**问题**：

1. `position` 本身只有季报值，中间会变 → 拟合出的系数不稳；
2. 需要至少 20~30 个连续的「净值与底层价格都对得上」的交易日；
3. QDII 净值滞后 1~2 天，对齐全靠猜；
4. 拟合出的 hedge 每天会抖，反而比矩阵公式更差。

**结论：花 1~2 周做出来的反推模型，精度不如直接用矩阵公式。不值得。**

### A.5 降级替代

**已实现**：矩阵公式（`_estimate_one`）。

两者在「单成分 + 基准价准确」时**数学等价**，差别只在
「是否依赖基准日选择」和「是否能吸收期现基差」。
doraemon 用日 K 收盘作基准，基准日是 `nav_date`（跨时区时 `nav_date - 1`），
这个近似在日终口径下误差 < 0.5%，完全可以接受。

### A.6 如果一定要做，前置条件

- [ ] 拿到 palmmicro 账号，能稳定请求 woody bot 接口（每日至少 1 次，连续 30 天不断）
- [ ] 建表 `fund_daily_factors(date, fund_code, calibration, hedge, position, nav)`
- [ ] 建表 `futures_daily(date, contract, calibration, ...)`
- [ ] 复刻 lofarb 的 `hedge_allowed()` 路由表（**必须做**，否则重现 10 倍 / 41 倍事故）
- [ ] 灰跑 2 周，用 §A.3 的误差口径验证：`|hedge估算 - 矩阵估算| < 0.3%` 才可切换

## §B · `calib` 期货期现折算 — 类别 A，不做

### B.1 它是什么

lofarb `realtime_futures_analysis.py` 有两种期货口径：

| 模式 | 公式 | 依赖 |
|---|---|---|
| **calib** | `equiv_spot = futures_price / calibration`，再用现货比价算净值 | `calibration` |
| **pure** | `est = nav × (1 + pos × (fut_now/fut_base × fx_now/fx_base − 1))` | 只要期货价 |

### B.2 为什么做不了

`calibration` 同上，只有 woody 有。

**但 pure 模式不需要它**，所以：
> doraemon **做 pure 模式**（todo.md T2），**不做 calib 模式**。

差别在于：calib 能把「期货升贴水」折算掉，pure 不能。
对白银（161226）、豆粕（159985）这类**商品期货型 LOF**，
期货贴水在换月时会突变，pure 模式会把它当成真实涨跌 → 误差突跳。
这是必须接受的代价。

### B.3 要什么数据

| 数据 | 用途 | 获取途径 | 成本 |
|---|---|---|---|
| 期货结算价历史（日） | pure 模式的 base | 网关 `futures_zh_daily_sina` | 免费 |
| 对应现货价 | 算 `calibration = 期货/现货` | 商品现货指数（生意社/卓创） | 付费，~1k/年 |
| 期现基差历史 | 换月时校正 | 无公开源 | 很难 |

### B.4 缓解措施

在换月前后 3 个交易日，对该类基金**直接拒绝估值**（返回 `None` 显示 `-`），
而不是给出被基差污染的数字。这符合铁律。

## §C · `trade_etf` 兜底估值 — 类别 A，不做

### C.1 它是什么

lofarb `fund_service.py` L2536-2538，当篮子成分缺失时，用「该基金对应的那个 ETF 的价格 + hedge」兜底：

```python
val_res = b_nav * (1.0 - b_position) + (etf_price * fx) / b_hedge
b_position = float(fund.get('pos_ratio') or 0.95)
```

### C.2 为什么不做

两个原因：

1. **依赖 hedge**（见 §A）；
2. **它的 `or 0.95` 违反铁律**——position 缺失时静默用 0.95 算出一个「看起来正常」的数。
   lofarb 自己的注释体系里明确写了「position 缺失返回 None，不兜底」，
   但这一行是历史遗留的破例。**doraemon 不应继承这个破例。**

### C.3 要什么数据

不需要额外数据，需要的是**不抄这段代码**。

## §D · 多时段锚点 `^USO-EU` / `^INDA-JP` — 类别 A+B，不做

### D.1 它是什么

lofarb 的篮子里有这类成分：

```yaml
valuation_portfolio:
  - symbol: ^USO-EU
    weight: 64.93
  - symbol: USO
    weight: 35.07
```

`^USO-EU` 表示「**同一只 USO ETF 在欧交所上市的份额，取它当日欧洲时段的收盘价**」。

**为什么需要它**：QDII 基金的净值基准时间点，不总是美股收盘。
例如 501018 南方原油，其净值反映的是「欧洲时段 + 美国时段」的加权价格。
只用美股收盘，会丢掉欧洲时段的涨跌。

### D.2 为什么做不了

**双重缺失**：

| 缺失 | 说明 |
|---|---|
| **符号体系**（A 类） | `^xxx-EU` / `^xxx-JP` / `^xxx-HK` 是 **woody 私有命名**，公开行情源不认识这个代码 |
| **交易所行情**（B 类） | 即使知道是「USO 在伦敦/法兰克福的代码」，doraemon 也没有欧洲交易所的行情源 |

### D.3 当前做法与影响

doraemon 的 `qdii_baskets.json` 已经把锚点**折叠进主板成分**：

```
501018: ^USO-EU 64.93 + USO 35.07  →  USO 100%
```

（配置里的 `_note` 有记录）

**影响**：丢掉「欧洲时段相对美股的额外涨跌」。
量级：同一 ETF 在不同交易所的价差通常在 **0.1~0.5%**，极端行情（欧洲先反应地缘事件）可到 2%。

**对日终信号的影响**：可接受。因为日终时欧洲和美国都已收盘，
主板价格已经包含了全部信息，缺的只是「加权方式」。

### D.4 要什么数据才能做

| 数据 | 具体 | 获取途径 | 成本/难度 |
|---|---|---|---|
| 欧洲上市 ETF 日 K | 如 USO 在 LSE/FWB/XETRA 的代码与收盘价 | ① 彭博/路孚特<br>② 交易所官网 CSV<br>③ Yahoo Finance（部分可用）<br>④ 富途/老虎（部分欧洲品种） | 中~高 |
| 日本上市 ETF 日 K | 如 1671.T / 1699.T | 雅虎日本（免费，lofarb 已用） | **低（可行）** |
| 权重分配 | 各时段权重（64.93 / 35.07） | woody 私有 | 高 |

**注意**：即便拿到行情，**权重从哪来仍是 A 类问题**。
权重本质是「该基金在不同市场的持仓分布」，只有基金公司或 woody 知道。

### D.5 折中方案（如果一定要做）

对**日本上市**的部分（`1671.T` / `1699.T` / `OILUSA`）：
lofarb 的 `usa_etf_history_sampler.py` 已经验证「雅虎日本 + SIX 官方 CSV」可行，
这部分**可以从 B 类降级为可做**。但权重仍需人工维护。

## §E · 欧洲 T 日组件（`eu_futures_store.t_day_component`）— 类别 B，不做

### E.1 它是什么

lofarb `fund_service.py` L~2500，QDII 欧洲基金（如 159561 德国 ETF）估值时：

```python
eu_futures_store.t_day_component(None, code, bd_eur.get('date'))
```

取「欧洲期货当日已经走完的那一段」作为 T 日组件。
因为 A 股收盘时（北京时间 15:00），欧洲还没开盘或刚开盘，
用欧洲「T 日已实现部分」+ 美股「T-1 收盘」拼出净值基准。

### E.2 为什么做不了

需要：
1. 欧洲期货（Euro Stoxx / DAX 期货）的**分时**数据；
2. 一张 `eu_futures_store` 等价的本地缓存表；
3. 「A 股收盘时刻 → 欧洲已交易多久」的时段切分逻辑。

doraemon 现在只有日 K，没有欧洲分时。

### E.3 要什么数据

| 数据 | 频率 | 来源 | 成本 |
|---|---|---|---|
| DAX / Euro Stoxx 期货分时 | 1 分钟 | IB / 富途 / 盈透 API | 开户 + 订阅费 |
| 或：欧洲指数日 K | 日 | 网关 `int_dax` / Yahoo | 免费 |

### E.4 降级替代

用**欧洲指数日 K 的 T-1 收盘**作为基准（todo T5 的做法）：
`est = nav × (1 + pos × (dax_now/dax_base − 1))`

**误差来源**：A 股 15:00 时，欧洲当日才交易了约 1 小时（北京时间 15:00 = 欧洲 08:00/09:00）。
用 T-1 收盘意味着**丢掉欧洲当日已走的部分**。
影响量级：约 0.2~1%（视当日波动）。

**结论**：接受。3 只欧洲基金不值得为此接 IB 分时。

## §F · 美股 tick 级盘中实时 — 类别 B/C，不做

### F.1 现状

doraemon `_fetch_us_realtime` 用新浪 `gb_xxx`，该接口在美股盘中会更新，
但**中国白盘时段（09:00-15:00）美股是休市状态**，返回的值 ≈ 上一交易日收盘。

所以 doraemon 的自算估值实际上是「**日终口径**」：
用「最新美股收盘 vs 净值基准日收盘」的比值，捕捉「净值尚未反映的隔夜新信息」。

**这本身是有效的信号**，只是不是「实时」。

### F.2 要做实时需要什么

| 方案 | 需要 | 成本 | 可行 |
|---|---|---|---|
| IB Gateway | 本机跑 TWS/Gateway + 美股行情订阅 | 账户 + 约 $10/月 | 可行但重 |
| 富途 OpenD | 本机跑 OpenD + 美股行情权限 | 账户 + 行情费 | 可行 |
| 长桥 | API | 账户 | 可行 |
| 付费 tick 源 | Polygon / IEX Cloud | $30~200/月 | 可行 |

### F.3 为什么不建议现在做

1. **中国白盘时段美股本来就休市**，tick 源也拿不到新数据 —— 这是时区决定的，不是技术问题；
2. 美股盘中（北京 21:30-04:00）时 A 股已休市，此时估值对 A 股交易**没有意义**；
3. 真正的增量在「美股收盘 → A 股开盘」之间，而这正好是日 K 能覆盖的。

**唯一有用的场景**：QDII 基金的**溢价套利在美股盘中做**（即在 A 股 T+0 场内卖出、同时美股盘中对冲）。
这需要 tick 源，且是另一个产品形态。**当前不做。**

## §G · 债券基金估值（501300 海富通美元债）— 类别 D，不做

### G.1 现状

`qdii_baskets.json` 里 501300 的 `basket` 为空、`currency: USD`、`position: 95`。

### G.2 为什么不做

债券基金的净值变动由**三件事**驱动，公开数据只能覆盖一件：

| 驱动因素 | 占净值变动比重 | 公开数据可得性 |
|---|---|---|
| 票息累积（carry） | 主要（每日稳定小幅） | ❌ 需持仓明细（票面、到期日、付息频率） |
| 利率变动（久期） | 主要 | ⚠️ 需组合久期，季报才披露，且滞后 |
| 信用利差 | 次要 | ❌ 需持仓债券的评级与利差 |
| 汇率（美元债） | 显著 | ✅ 有 |

**核心问题：拿不到「组合久期」的日频值。**
没有久期，就无法把「美债收益率变动」换算成「净值变动」。

季报披露的十大重仓债券只占组合的 30~50%，且日期滞后 1 个季度。

### G.3 要什么数据才能做

| 数据 | 频率 | 来源 | 难度 |
|---|---|---|---|
| 全部持仓债券（代码/面值/到期日/票面/评级） | 季（滞后） | 基金季报 PDF / 中国货币网 | 需要 PDF 解析 |
| 组合久期（duration） | 季（滞后） | 季报「风险收益特征」段落，常缺失 | 高 |
| 对应债券的日频估值净价 | 日 | 中债登（需付费）/ Wind / 聚源 | 付费 |
| 美债收益率曲线（若持美债） | 日 | 网关有，或 FRED | 免费 |

### G.4 lofarb 自己的做法（可参考但不可直接搬）

`bond_etf_valuation.py` 用的是**日均增长法**——根本不看持仓：

```
estimated_nav = 最新净值 × (1 + 日均增长率 × 距净值日天数)
其中日均增长率 = 最近 20/30 个交易日的净值日均增长
周末按 3 倍
```

**这是「用历史净值外推」**，本质上不是估值，是趋势延续。
而且——**lofarb 侧这个文件已经迁出到 ETFarb 了**（2026-09-18），
LOFarb 的 `/api/bond/*` 已改为返回 `{"status":"moved"}` 的路径壳。

**结论**：连 lofarb 自己都不再维护这条路，doraemon 更没必要接。

## §H · 历史 `est_nav` 回补 — 类别 C，部分做

### H.1 想做什么

### H.2 为什么 doraemon 只能部分做

| 需要的输入 | 历史可得性 |
|---|---|
| 基金历史净值 `nav` | ✅ 有（`fund_open_fund_info_em` 可回溯全历史） |
| 底层 ETF 历史收盘 `P_base` | ✅ 有（新浪 `US_MinKService.getDailyK` 可取 60 根） |

- 若该基金在这 40 天内换过仓 → 回算出来的历史 `est_nav` 是**假的**
- 误差曲线会显示「过去一直很准，今天突然不准」——完全误导

### H.3 结论与做法

- **不回补历史**（会造假）
- **从今天开始逐日积累**（todo T3.3a：每日收盘后落快照）
- 积累满 20 个交易日后，误差曲线才有统计意义

### H.4 如果一定要回补，需要什么

| 数据 | 说明 | 来源 |
|---|---|---|
| 历史 position 时间序列 | 每季一个值，需知道生效日 | 基金季报（PDF）× N 季度 |
| 历史篮子权重时间序列 | 同上 | 同上，且需重建成分股清单 |
| 或：历史 `fund_basket_weights` 快照 | lofarb 有这张表 | **向 lofarb 生产库索取导出** |

**这是唯一可行的捷径**：如果 lofarb 的生产库还活着，

### N.2 为什么做不了

**不是算不出来，是算出来没用。**

### O.2 为什么不做

- 另 3 只的超标日是**孤立事件**：513880 一天都没有；159866 只有 7-8/-1.173% 与

  → **是基金自身净值口径拖动的，不是指数解释力不足**，其他 100+ 天都干净。
- 513520 是**散布型**：71 天里 14 天超 0.5%（20%），Top5 分布在 7-07 / 7-21 / 8-03 /
  8-04 / 9-03，没有成对抵消，也不是某一天的事故。这说明它对日经 225 的跟踪本身就松
  （beta 实测 0.957，低于另 3 只的 0.963~0.990）。

换个口径也救不回来：4 种对齐穷举下，它只有「指数当日 × 汇率当日」可用（beta 0.940 / R² 0.965），
其余三种 beta≈0。而这一口径下它的残差 0.352%、前向误差 0.307%，两者都停在门限边上。

**按铁律：残差 ≥0.3% 时噪声能吞掉 LOF 典型 0.5% 溢价的大半，出数会误导，所以显示 `-`。**

### O.3 要什么数据才能做

任何**一项**到位即可重新评估：

1. **该基金的实际持仓**（季报十大重仓 + 现金/互换占比）——判断它到底是不是 100% 复制日经 225，
   还是用了互换/部分现金（那样 position 与 "指数" 之间就差一个真实的结构），
   数据源：基金季报 PDF / 交易所定期报告。
2. **基金公司公布的估值汇率**（它到底用中间价还是即期）——若它用即期，则我们的中间价就是错的。
3. **更长的样本**（≥250 个交易日）——71 天的 beta 估计本身有误差；若长期 beta 稳定在 0.96 附近
   且残差回落，可以重新标定后放入。

#### P.3.3 代码怎么处理的

`_load_jp_daily_sync` / `_jp_daily_load` / `_jp_daily_kick` / `_fetch_jp_index_daily`：

- 「慢腿 + 后台预热」：`TTL 4h`、失败退避 **60min**、`retries=1`；刷新永远在后台线程，
  **主快照只用当前缓存**（否则 52~92s 会把美股/港股/期货一起拖住）；
- 失败时**保留旧缓存**、不清空；首次失败则日经暂不出数（前端显示 `-`）；
- 删掉了日经实时腿（`_fetch_jp_index`）：网关没有日经实时，现值改由日K末根承担
  （日本 14:00 收盘，A股收盘后即当日收盘）；
- `_estimate_by_index` 里加了 `daily[-1][0] <= nav_date → return None`，
  防止 14:00 前退化成 `est_nav = nav` 的假估值。

退避从 10min 放宽到 60min 是因为确认了「长期故障」而非「偶发抖动」：一轮失败要烧 92s，
10min 退避等于一天 7 小时空转后台线程；60min 退避下一天最多 24 轮 ≈ 37 分钟，
网关修好后仍能在 1 小时内自动恢复。

**结论：日经 3 只（513000/159866/513880）现在「网关有数就出、没数就不出」。**

### P.7 网关抖动时会出现什么：`price_kind` 停在 `live`

网关不是「通 / 不通」两态，而是长期抖动（2026-10-30 14:31 又见 `fund_rank` 三次超时、
`futures_zh_daily_sina` / `futures_zh_spot` 双双超时）。表现为：

1. `_ensure_snapshot` 的 5 分钟 TTL 到期后**刷新失败 → 保留旧快照**（设计如此，宁可出旧数不空着）；
2. 若旧快照里的日K末根仍停在 `nav_date`，`_estimate_by_futures` 就走 `live` 分支（实时价），
   输出 `est_futures_price_kind = live`；
3. 于是**同一只基金、同一个净值，白天看是 `live`、晚上看是 `settle`**，数值会差 0.1~0.6%。

**这不是 bug，是必须知道的口径特征**：`est_futures_price_kind` 就是用来标识这一点的，
前端 tooltip 已展示。若发现某天一直是 `live`，应该去看网关，而不是改代码。

对照实测（159985，nav=2.1129 / nav_date=2026-10-28 / position=88.9）：

| 快照状态 | 用价 | `price_kind` | `est_nav` |
|---|---|---|---|
| 新鲜（日K末根 = 10-29） | 结算 3181 | `settle` | **2.0965** |
| 陈旧（日K末根 = 10-28） | 实时 3161 | `live` | **2.0848** |

两份数字差 0.56%，而真实净值日还是 10-28 —— 说明宁可先出 `live` 也比不出数有用，
但**跨日对比时必须用同一 `price_kind`**，否则会误判精度。

LOF/ETF 在交易所挂牌，直觉上股票日线接口应该认。实测**全不认**：
`stock_zh_a_daily` / `stock_zh_a_hist_tx` / `stock_zh_a_hist` 传 `164705` / `513000`
一律 3s 左右 500。而同一时刻 `stock_zh_index_daily(sh000001)` 1.3s 成功 ——
说明不是网络问题，是**这些方法在网关实现里对基金代码直接拒**。

### Q.4 所以代码必须是两段式（已实施）

| 段 | 覆盖 | 取数 | 直连? |
|---|---|---|---|
| 第一段 | ETF 口径（日经 3 只） | 网关 `fund_etf_fund_daily_em` 一次批量 + 自带净值 | **零直连** |
| 第二段 | LOF 口径（164705 等 5 只） | 新浪报价（直连）+ 网关 `fund_open_fund_info_em` 净值 | 报价直连 |

**硬规则（已写进代码）**：ETF 条目在网关没命中时**不得回退直连**，宁可不显示。
第一版会静默回退，被抖动窗口实测抓到（网关 degraded 时 `fund_etf_fund_daily_em` 也超时，
于是 513000 悄悄改走了新浪）—— 那等于「零直连」的承诺在故障时自动失效，必须堵掉。

### Q.5 还有两个被这次实测暴露的旧隐患（已修）

1. **逐只净值无熔断**：单只超时 25s，8 只全挂在网关 degraded 时会占住后台预热线程 **260s**，
   期间缓存一直是空。已改为连续 2 只失败就中止本轮。
2. **预热失败锁 1 小时**：`_warm()` 无论成败都写 `ts=now`，配合 `TTL=3600` →
   网关抖一下就造成 **1 小时空窗**。这也解释了「明明有估值却整行不显示」为何会持续很久。
   已改为：全空时 5 分钟重试，并保留上一轮旧行。

### Q.6 要彻底解决还需要什么

按优先级：

1. **网关放通 `fund_lof_spot_em`**（或给 ETF/Lof 合一的场内行情）—— 一条就能让 161226 也进来；
2. 或者给一个「按代码批量取场内实时价」的方法（现在能用的只有全市场口径，且都走 push2his）；
3. 顺带：`fund_etf_fund_daily_em` 现在 16:00 后才更新当日数据，**盘中拿到的是昨日收盘**。
   若需要盘中实时折溢价，得靠上面第 1/2 条。

在拿到上面任一条之前，**161226 不会出现在页面上** —— 它属 LOF 口径但网关无市价源，

## §R · 估值误差自检（T3）不能做的事

#### R.1 不复用 `ensure_fund_nav()` 的净值腿（T3）

`fund_extra_metrics_service.ensure_fund_nav()` 已经在拉真实净值 —— 直觉上
`valuation_error` 回填应该直接蹭它，但**不能**：

- 它走 `pingzhongdata` **直连**，与本轮「一律走网关」的要求冲突；
- 它的语义是「给增强指标补净值」，入库到 `base_fund_nav`，生命周期与估值历史不同；
  搭车会让“为了一个指标刷新而改动另一张表”的隐式耦合扩散。

所以 T3 用网关 `fund_open_fund_info_em` 自己取（实测 0.59~1.98s/只、全历史 1688~3068 天），
代价是每晚多打 N 次网关；换来的是 T3 **零新增直连**（已隔离在 `_fetch_nav_map` 一个函数里，
将来换成别的源只改这一处）。

#### R.2 不用方案 B（在 `fund_extra_metrics` 加列）

方案 B 改动小，但 `fund_extra_metrics` 的写入语义是**整行 upsert（只保留最新一天）**，
把每日估值塞进去会被反复覆盖 —— 误差自检恰好需要「每日一行、长期保留」才能看趋势
与判「突然变大」。所以新建独立表 `fund_est_nav_history`，不碰现有指标表。

#### R.3 回补不了历史（至少今天做不了）

T3.3-c 提到的「回算过去 40 个交易日」**目前不可做**：需要那 40 天当时算出的 `est_nav`，
而我们从未落库；用今天的 `qdii_baskets.json` 回猜历史权重等于伪造历史（参考 §H）。
因此**只能从上线日开始积累**：首日全列 `-` 是设计而不是 bug。

#### R.4 没有样本就不写字段（绝不写 0）

`0` 会被前端/人读成「零误差，很准」，比显示 `-` 危险得多。所以 `attach_valuation_errors`
只对有回填样本的基金写字段；`valuation_error_n` 同时透出，前端 tooltip 用「近 20 日样本 N 个」
标明样本量，让人自己判断可信度。

#### R.5 不在 `/funds` 里同步回填

`/funds` 是全市场扫描型接口（几千行）。若在其中回填，每只基金一次网关请求（1~2s）
会把接口拖到分钟级。所以只读 120s 缓存的汇总，回填独立成定时任务（03:00）。

#### R.6 失败不写「放弃」标记的取舍

取不到净值就让它继续 `NULL`，下轮重试。好处：QDII 净值滞后 1~2 天公布时能自动补上。
代价：`BACKFILL_MAX_CODES` 之外的永远不会处理，窗口外的（>30 天）也不会回头；
若某只基金长期无净值，会每晚白打一次网关 —— 在 80 只上限内可接受，
若基金池扩到 T6 的 40+ 只且多数失败，需要加「连续失败 N 次退避」。

#### R.7 DuckDB 单写连接：两个 job 不能并发写

`database/connection.py` 是「单写连接 + RLock」模型。`est_nav_snapshot`（15:30）与
`est_nav_backfill`（03:00）时间上不重叠，但如果手动触发撞在一起，写会在锁上排队——
正确但会变慢。**不要**为了“提速”绕开 `db.executemany` 直取 `db.conn`，
那会重蹈 2026-10-15 的并发写段错误（参考 §P.5 的 WAL 事故同类风险）。

#### R.8 快照 job 不能吃 `/funds` 的 30s 列表缓存

`get_funds()` 有一层 30 秒列表级缓存（`_FUNDS_LIST_CACHE`，`fund_service.py` L469）。
快照 job 最初写成 `get_funds("all")`，看起来省力，实际上是个**不可恢复的坑**：

- 服务刚启动的 1~2 分钟内，估值慢腿（美股序列 / 港股指数 / 期货）还没预热完，
  此时 `/funds` 算出来的 `est_nav` 全为 `None`；
- 只要这个空结果在 30 秒缓存有效期内被任何一次页面请求写入缓存，
  15:30 的定时快照就会**原样读到空结果**，落 0 行；
- 而 `est_nav` 是「当时的快照」，过了那天就补不回来（§R.3），
  等于永久性丢掉一天的误差样本 —— 偏偏这种丢法在日志里只表现为
  「快照写入 0 行」，很容易被当成「今天没有估值」放过去。

**修法**：`_job_snapshot` 里固定 `get_funds("all", force=True)`，穿透缓存重扫。
代价是每次多花十几秒（实测 23 只口径下 1.1s ~ 14.8s），收益是历史不留空洞。
实测对照：修前手动触发 → `快照写入 0 行`；修后同一天再触发 → 落 23 行。

2026-10-31 实测：服务启动约 60 秒内 `/funds?type=all&force=1` 返回 0 只有 `est_nav`，
等到 2 分钟后同一请求返回 23 只 —— 冷启动窗口真实存在，不是偶发。

## §S · 后端重启时的 DuckDB 安全流程（2026-10-31 实测）

§P.5 记录过「强杀进程导致 WAL 损坏」的事故，留下的
`quantterminal.duckdb.wal.broken_20261029` 至今还在目录里。本节是踩过之后总结的
可执行流程，三步都要按顺序做。

#### S.1 先试优雅关闭，不要上手就杀

Windows 上没有 Linux 那种「给 pid 发 SIGTERM」的现成通道，但可以借控制台信号：

```
FreeConsole()                       # 脱离自己的控制台
AttachConsole(pid)                  # 附加到目标进程的控制台
SetConsoleCtrlHandler(NULL, TRUE)   # 先让自己忽略 Ctrl+C，否则先把自己干掉
GenerateConsoleCtrlEvent(0, 0)      # CTRL_C_EVENT 发给该控制台所有进程
```

脚本：`.stage_doraemon/_graceful_stop.py <pid>`。

实测效果（PID 47980）：3 秒内退出，日志出现 `Application shutdown complete` +
`Finished server process`，**`.wal` 文件消失、`.duckdb` 从 6.76MB 变成 13.01MB** ——
这就是 WAL 被正常 checkpoint 合并进主库的证据，也是强杀永远得不到的结果。
所以只要还能发 Ctrl+C，就必须先发。

#### S.2 主线程结束后，残留的后台线程会把库重新打开

优雅关闭完成后 uvicorn 会打印 `Finished server process`，但**进程可能还活着**：
`lifespan` shutdown 只负责 `stop_*_scheduler()`，管不到已经在跑的启动补跑线程
（FundHold / DividendIdxMap / ExtraMetrics 等，都不是 daemon 线程）。这些线程下一轮
循环调用 `get_db()` 时，单例会**重新建立写连接**，文件锁又回来了，于是新进程起不来：

```
_duckdb.IOException: IO Error: Cannot open file "...quantterminal.duckdb":
另一个程序正在使用此文件，进程无法访问。
File is already open in D:\Python310\python.exe (PID 30624)
```

这时再发 Ctrl+C 是没用的 —— 主线程已退出，没人处理这个信号（实测连发两次，
15 秒仍不退出）。只能 `Stop-Process -Id <pid> -Force`，但**必须先做 S.3 的判定**。

#### S.3 能不能强杀，只看一件事：WAL 是否已经归零

```powershell
Get-ChildItem D:\workspace\doraemon\backend\database\quantterminal.duckdb* |
    Select-Object Name, Length
```

- `.wal` 不存在或 0 字节 → 所有写都已 checkpoint 进主库，强杀只丢内存态，文件安全；
- `.wal` 有体积 → 说明存在未落盘的写，强杀后只能靠重启时 replay 恢复；
  replay 失败就是 §P.5 那种结局。这种情况应该**等当前后台任务跑完**，或者
  直接放弃这次重启（服务还在正常跑，不必急在这一分钟）。

绝不做的事：移动、重命名、删除 `.wal` 文件。§P.5 事故的直接诱因就在这里。

## §T · 对照 palmmicro《估值说明文档》的审计结论（2026-11-01）

来源：用户提供的 `估值说明文档.md`（palmmicro 站内抓取，2026-10-28 快照，
覆盖 135 只详情页）。用它逐条校验我们的 4 种估值口径，结论 + 已改 + 取不到数据的缺口。

### T.0 一句话结论

我们的骨架和 palmmicro **完全一致**：都以「最近一次官方公布净值为锚 ×（1 + 仓位 × Δ标的）×（1 + Δ汇率）」。而且我们**每天用最新官方净值重新锚定**，天然规避了 palmmicro 自己的头号顽疾 ——「校准值卡在旧日期」（3.15④：中美轮流休市触发错误校准，513800 的 EST 停在 2025-09-29，页面照样给出 28.56% 的**假溢价**）。我们没有静态校准值，所以不会犯这个错。

### T.1 已修的口径错误（本次改代码）

**Δ汇率过去被 position 缩放了**。旧公式 `nav*(1+pos*(Σw·ratio·fx_ratio−1))` 把汇率项也乘了仓位；
文档 2.2 / 3.3 / 3.5 / 3.6 / 3.7 每一处通用式都是 `前日净值×(1+仓位×Δ标的)×(1+Δ汇率)` ——
汇率乘**整块净值**、不打仓位折扣（因为 QDII 的现金头寸也是外币，全额吃汇率）。

- 改后：`growth = Σ w_i·((1+pos·(ratio_i−1))·fx_ratio_i − 1)`；`est = nav·(1+growth)`。
- 单币种时精确等于文档式 `nav·(1+pos·Δ标的)·fx_ratio`；多币种篮子（160644）逐组件各折各的汇率。
- **index / futures 两条腿改后与改前逐字节相同**：JP 日经走合腿序列 + `currency=CNY`、内盘白银/豆粕 `currency=CNY`，`_fetch_fx` 里 `CNY={now:1,base:1}` → `fx_ratio=1`，实测 diff=0（见下验算）。只有 USD/HKD 单币种基金变化，量级 +0.0035%~0.025%，远低于 T3 噪声底 ±0.11%。
- 脚本：`_apply_fx_fix.py`（备份 `cross_border_valuation.py.bak_fxfix`）。

顺带放开 **513350 富国标普油气**：文档 8.2 给它仓位 1.00（ETF 满仓），与已上线的 159518 同一 XOP 篮子、数据已具备 → 去掉 `uncertain`，`position=100.0`。原 lofarb yaml 无 position 才标的不估算。

**汇率腿改用人民币中间价（严格对齐文档 3.15③/5.2）**。文档钉死「基金净值公告用美元人民币**中间价**、非在岸即期」（华宝油气与官方偶发 0.1 分误差即源于此）。旧实现 USD/HKD 走新浪即期 `fx_susdcny/fx_shkdcny`（仅 JPY 腿用中间价）；现 `_fetch_fx` 的 USD/HKD/JPY 一律取网关 `currency_boc_safe` 中间价日序列的**最近两日比值**（今日/昨日），新浪即期降级为「中间价缓存空」时的兜底。

- 取的是比值 `fx_now/fx_base`，中间价「100 外币兑人民币」的量纲相除即约掉，无需 /100；
- 中间价日频、盘中不动 → 与文档「参考 EST 用日频中间价、盘中变化全来自标的」口径一致，比即期更贴净值公告；
- **CNY 路径逐字节不变**：`out["CNY"]={now:1,base:1}` → `fx_ratio=1`，futures(161226/159985)、日经(currency=CNY) 的 est_nav 不受影响；
- 自测（`_selftest_doc_align.py`，2026-10-30 中间价）：USD 671.38/671.47=0.999866、HKD 85.594/85.596=0.999977、JPY 4.2419/4.2453=0.999199，三币种均 `src=boc_mid`、CNY=1 → PASS；
- 脚本：`_apply_doc_align.py`（备份 `cross_border_valuation.py.bak_docalign`）。原 T.2.8 缺口据此关闭。

**禁用 160216 国泰大宗商品（严格对齐文档 3.12/附录）**。文档对照表钉死 160216 = 黄金多头(GLD/IAU +1、UGL +2) + 白银空头(ZSL −2) + 原油空头(SCO −2)，同时挂 GC/SI/CL 三组；而本配置 SLV(银**多**)67.93 + USO(油**多**)32.07 —— **三腿方向全反、且缺黄金腿**，折叠成多头代理会给出方向性错误的 est。文档主方法是 holdingscn 成分股漂移法，真实持仓🔒需登录、网关 `fund_portfolio_hold_em` 对 160216 返回 0 行(2026/2025 均空) → 无法复现。按铁律「缺篮子/持仓不估算」禁用：`position=null`+`uncertain=true`、前端 '-'（保留篮子仅留痕）。详见 T.2.5。脚本同上 `_apply_doc_align.py`。
