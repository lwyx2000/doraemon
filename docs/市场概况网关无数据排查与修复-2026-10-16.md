# market/overview 长期显示「网关无数据」排查与修复（2026-10-16）

## 现象

`http://10.100.213.248:9080/api/v1/market/overview` 持续返回：

```json
{"status":"数据获取中","indices":[],"gatewayEmpty":true,"dataSource":"网关无数据"}
```

Dashboard 市场概况区块长期空态。

## 根因链（三层，逐层有证据）

### 1. 网关侧：两个热 category 的冷首算超过 `wait_for` 上限 → 504

实测（curl 直连网关 `10.100.213.248:8000`）：

| 请求 | 结果 | 耗时 |
|------|------|------|
| `processed_data?category=index_valuation` | `{"code":504,"message":"index_valuation 查询超时"}` | 120.07s（等满上限） |
| `processed_data?category=market_stats` | `{"code":504,"message":"market_stats 查询超时"}` | 30.06s（等满上限） |

- `processed_data.py` 用 `asyncio.wait_for(run_in_executor(...))` 包住同步计算：
  index_valuation 上限 120s、market_stats 上限 30s。
- index_valuation 冷算 = baostock 批量日线（12 指数单次登录）+ 8 次中证官网 PE 历史
  （串行，每次 timeout=7，慢时最坏 56s）+ 腾讯实时 PE + 新浪指数行情 + 国证 PB，
  合计可逼近甚至超过 120s。
- market_stats 冷算 = 新浪全A股 `stock_zh_a_spot()`（5500+ 只、70+ 页）+ 指数行情，
  冷抓经常 >30s。
- `wait_for` 超时返回 504，但 **executor 线程会继续跑完并写缓存**，所以网关能自愈
  （复测：缓存写热后同一请求 0.1~2s 返回完整数据）——但冷窗口内的请求全部 504。

### 2. doraemon 侧：客户端超时比网关能成功的用时还短 → 「慢而能成」也被丢弃

- `_fetch_index_valuation_raw` 用 `timeout=15` 打网关；网关冷算 50~120s 内本就该成功，
  doraemon 15s 主动断开 → 拿到空。
- `get_market_stats_real` 用 `timeout=10`；同理。
- 两个都失败时 `get_market_overview_with_meta` 走「数据获取中」+ `gateway_no_data_meta()`
  （market_service.py:1167 附近），即用户看到的现象。
- 且两者**串行**调用，冷启动最坏 15+20=35s+ 才返回失败态。

### 3. 叠加因素

- 无负缓存（设计正确）：每次轮询都重新撞冷窗口，故障观感被拉长。
- 冷窗口期间前端每 30s 轮询 overview，持续拿到 504 → 「一直显示」。

## 修复

### doraemon（backend，本次提交）

| # | 改动 | 文件 |
|---|------|------|
| 1 | index_valuation 上游超时 15s → **130s**（> 网关 120s 上限，慢而成功的调用不再被误杀；singleflight 跟随等待 45s → 145s） | `services/market_service.py` |
| 2 | market_stats 上游超时 10s → **35s**（> 网关 30s；retries=2 保留：第一次 504 时网关线程已写热缓存，第二次秒回） | `services/market_service.py` |
| 3 | overview 两个上游**并行**（ThreadPoolExecutor(2)）：冷启动最坏 200s → 130s | `services/market_service.py` |
| 4 | **启动预热**：lifespan 起后台线程打一遍两个上游，把网关冷算成本挡在启动期，首个用户请求不再干等 | `main.py` |

### 网关 akshareProject（backend/src，本次提交）

| # | 改动 | 文件 |
|---|------|------|
| 1 | market_stats 执行上限 30s → **120s**（冷抓全A股常 >30s，原上限误杀慢而能成的请求） | `api/routers/processed_data.py` |
| 2 | index_valuation 冷算中 8 次中证官网 PE 历史改 **4 并发预热**（串行最坏 56s → ~15s），冷算总耗时远离 120s 上限 | `datasource/index_valuation_service.py` |
| 3 | **日内保温任务**：交易日 08-16 点每 8 分钟，早于 TTL（idx 10min / stats 5min）主动重算，带新鲜度守卫（刚被请求刷新过则跳过）——把冷算成本从请求路径挪到定时任务，请求侧永远命中温缓存 | `api/tasks.py` + 两个 service 各加一个 `*_cache_age()` 辅助 |

## 验证

- doraemon：`scripts/test_index_val_cache.py` 20/20 通过（TTL/singleflight/无负缓存/
  enrich 并行/overview 并行合并与降级分支）；`py_compile` 通过。
- 网关 service 层离线测试通过（prewarm 并发峰值 4、跳过已缓存、过滤无 PE 历史源符号、
  cache_age 正确）；四个改动文件 `py_compile` 通过。
- 线上实测：网关缓存热后 overview 恢复完整数据（12 指数 + 涨跌家数，`已收盘`）。
- 端到端待网关部署新代码后复盘：观察 08-16 点每 8 分钟保温日志
  （`processed_data 保温完成: ...`）与 overview 504 是否绝迹。

## 遗留 / 后续可选

- index_valuation 的 `get_all_index_valuation` 无 singleflight：保温 job 与请求瞬间
  并发时会双份冷算（各写各的缓存，无正确性问题，仅多打一次上游）。如需可加 Event 去重。
- market_stats 的新浪全A股抓取无显式超时（akshare 默认），源站 hang 时会拖满 120s；
  可在网关侧包一层显式超时。
