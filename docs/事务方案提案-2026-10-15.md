## 一、问题重述

`Database` 包装器（`backend/database/connection.py`）无显式事务，DuckDB 连接为 **autocommit**——每条 `execute` 独立提交。凡「DELETE 旧数据 + INSERT 新数据」组合，若 INSERT 中途失败（脏数据、磁盘、上游返回结构异常等），结果是**旧数据已删、新数据只写一半**，且无自动恢复。

- 本轮 11 处批量写修复**未恶化**此窗口：原 `executemany` 同为逐行提交；且 etf / pe 两处已改无 DELETE 的 `ON CONFLICT DO UPDATE`（失败不动旧数据）
- 但窗口本身仍在，且有两个大爆破面（持仓、净值），值得一次性收口

## 三、设计约束（来自 connection.py 现状，提案必须尊重）

1. **单写连接 + RLock 串行化**：所有写走同一连接、同一把可重入锁——事务必须**持锁跨 BEGIN...COMMIT**，否则他线程的写入会被吞进本事务（共享连接，DuckDB 事务按连接计）
2. **线程级只读连接 + MVCC**：读不走写连接——**事务内 read-back 不可用**（读的是未提交快照之外的旧快照），事务块内禁止 `fetch*`
3. **并发写者真实存在**：APScheduler 默认 10 线程池 + 多个服务自有 `ThreadPoolExecutor`（dividend PE 回填、market 2 线程等）——事务持锁期间他线程写者排队（不报错，只是等）
4. 全项目**当前零事务使用**（grep BEGIN/COMMIT 无命中），无历史包袱

## 四、候选方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 事务上下文管理器** | `Database.transaction()`：持写锁 → BEGIN → yield → COMMIT/ROLLBACK | 语义与现完全一致；机械替换；已 POC 全验证 | 持锁期间阻塞其他写者（批量越大越久） |
| **B. ON CONFLICT 化** | 破坏性 DELETE 改 `INSERT ... ON CONFLICT DO UPDATE` | 根除窗口；失败不动旧数据；语义上「合并」往往比「替换」更稳 | 仅适用合并语义可接受的表；持仓（精确替换）不适用 |
| **C. 自愈重试** | 接受瞬时窗口，失败由 job 重跑修复 | 零架构改动 | 窗口期数据缺失/错误直接暴露给前端；依赖 job 频率与上游仍可取 |
| **D. 暂缓** | 不动 | 零风险 | 窗口持续存在 |

### 批 1（收益最大，优先）：A2 净值改 ON CONFLICT（方案 B）

db.execute("DELETE FROM base_fund_nav WHERE fund_code = ? AND trade_date < ?", [code, cutoff])
bulk_insert(db, "INSERT INTO base_fund_nav (fund_code, trade_date, nav, daily_growth) "

### 参考实现（POC 已全验证，见下）

```python
@contextmanager
def transaction(self):
    """显式事务：持写锁跨 BEGIN...COMMIT（共享单写连接，必须持锁防他线程写入被吞）。
    ⚠️ 事务块内禁止 fetch*（线程读连接 MVCC 读不到未提交数据）。支持嵌套（深度计数，最外层统一提交）。"""
    if getattr(self, "_tx_depth", 0) > 0:
        self._tx_depth += 1
        try:
            yield
        finally:
            self._tx_depth -= 1
        return
    with self._write_lock:
        self._tx_depth = 1
        self._write_conn.execute("BEGIN")
        try:
            yield
        except Exception:
            try:
                self._write_conn.execute("ROLLBACK")
            except Exception:
                pass
            raise
        else:
            self._write_conn.execute("COMMIT")
        finally:
            self._tx_depth = 0
```

## 七、风险与缓解

| 风险 | 缓解 |
|---|---|
| 持锁阻塞其他写者 | 各点持锁时长已测量（holdings ~2s / longterm ~14s）；无超时机制只是排队；批 3 longterm 可择「维持+文档化」 |
| 事务内 read-back 踩雷 | 代码审查清单 + 注释铭文；POC#5 已证明行为 |
| 嵌套开事务 | 深度计数放行（POC#6）；文档规定事务块内不调其他开事务函数 |
| ROLLBACK 自身失败 | 参考实现吞 ROLLBACK 异常、重抛原异常（不掩盖业务错误） |
| mock 模式 | 涉事函数 mock 分支均不触库（已核 `_persist`/`_ensure_fund_nav` 调用链），事务代码只在非 mock 路径 |
