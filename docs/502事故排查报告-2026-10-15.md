# 宏观看板 502 事故排查报告（2026-10-15）

## 一、故障现象

- 宏观看板（`/dashboard`）大量接口同时 502，同秒 11 个看板端点全部 `Connection refused`
- backend 容器崩溃循环：每 60-90 秒 `Segmentation fault (core dumped)` 一次，RestartCount 10→16 持续累加
- 崩溃**无 Python traceback**，重启后 lifespan ~28-43s，期间 nginx 整页 502

## 二、诊断时间线

| 阶段 | 动作 | 结论 |
|------|------|------|
| 1 复现 | 并发批次重放 11 个看板端点 + 轮询 RestartCount | 100% round 1 崩，必现 |
| 2 修正检测模板 | `{{.State.RestartCount}}` 报 template parsing error（该 docker 版本不支持），RC 全空导致二分脚本"盲跑还输出 survived" | 改用 `{{.RestartCount}}`，重跑 |
| 3 端点二分 | 前半组崩、后半组 6 轮干净 → 收敛到 `{sw-sectors, overview, indices}` → `{overview, indices}` 干净 | **`market/sw-sectors` 是唯一必需端点** |
| 4 faulthandler | compose 加 `PYTHONFAULTHANDLER=1`，段错误时 dump 全线程 Python 栈；`Current thread` 标注 = 出事线程 | 出事线程在 `connection.py:108 executemany` 写路径 |
| 5 单端点验证 | `sw-sectors?force=1`（穿透 10 分钟缓存）第 1 发即崩 | **与并发读无关，写入本身有毒** |
| 6 假设证伪 ×3 | ① 读连接回退写连接无锁（加锁后仍崩、诊断零触发）② duckdb 1.5.5→1.5.6（仍崩）③ 写入形态 bulk_insert↔executemany（都崩） | 三个假设全部排除 |
| 7 生产库副本隔离实验 | 把生产 `.duckdb`+`.wal` docker cp 进容器，容器内 python 直接写探针 | **同库新表 OK、`base_fund_fee_info` OK、`base_etf_subscription_daily` OK，唯独 `base_sw_sector_daily` 写即崩** |
| 8 定表 | DROP `base_sw_sector_daily` 后 FORCE CHECKPOINT 恢复正常 | **全库仅此一张表存储块损坏** |

### 副本隔离实验矩阵（同容器、同 duckdb、同文件副本）

| 变体 | 结果 |
|------|------|
| A 纯重开不写 | 干净 |
| B 无 WAL | 干净 |

## 三、根因

**`base_sw_sector_daily` 表磁盘存储块损坏**（全库仅此一张）。任何写入该表的操作——INSERT / UPSERT / executemany / bulk_insert（字面量多行 VALUES）/ FORCE CHECKPOINT——都触发 duckdb native 段错误。

因果链：
```
表存储块损坏 → 写 sw-sectors 端点 duckdb native 段错误
→ backend 每 60-90s 崩溃（崩溃时 lifespan 启动任务 ~30-60s）
→ 重启窗口 nginx 全 502 → 用户看到整页 11 个接口同时加载失败
```

触发路径：`market/sw-sectors` 是唯一写库的看板端点（10 分钟缓存，未命中才写 `_save_sw_sector_snapshot`），所以表现为"看板偶发大面积 502"而非固定失败。

**与以下因素无关**（均经实验证伪）：并发读写、读连接回退路径、duckdb 版本（1.5.5/1.5.6）、写入形态（字面量 vs 参数化）、10-14 的 11 处写路径优化。

## 四、修复

`database/init_db.py` 新增 `repair_sw_sector_table(db)`：CTAS 备份 → DROP → 按 `schema.py` 原 DDL + 索引重建（复用 `TABLES`/`INDEXES` 常量防 DDL 漂移）→ `INSERT...SELECT` 灌回（PK 列走 DEFAULT nextval 不显式插入）→ 删备份。env `REPAIR_SW_SECTOR_TABLE=1` 一次性门控，挂 `main.py` lifespan（`ensure_schema` 之后）。

生产执行结果：**备份 7965 行 → 恢复 7965 行**，数据无损。

### 修复中的坑（重要教训）

1. **修复函数末尾的 `FORCE CHECKPOINT` 在生产库上 native 空转**（99% CPU 无进展 7 分钟）：生产 WAL 含崩溃循环期间写入的残留条目，checkpoint 合并时卡死——是**纯 hang 而非异常，try/except 抓不到**，lifespan 卡死导致服务持续 502。最终用 `docker exec python -c "import os,signal; os.kill(7, signal.SIGABRT)"` 触发 faulthandler dump 定位到 `init_db.py:339 FORCE CHECKPOINT`，随后从修复函数中删除该步骤（DROP/INSERT 均 autocommit 已落 WAL，数据安全不依赖 checkpoint；WAL consolidation 交给 duckdb 自动 checkpoint）。**函数内已写注释警告，禁止再加回来。**
2. 信号发送三连败后才找到可行路径：宿主 `kill` 无权限（容器进程 root 所有）→ `docker exec kill` 不存在（slim 镜像无 kill 二进制）→ `docker kill -s ABRT` 只打 PID 1（sh 包装器）→ **`docker exec doraemon_backend python -c "import os,signal; os.kill(<pid>, signal.SIGABRT)"` 成功**。

## 六、附带改动（防御性，与本事故无关但已保留）

1. **`connection.py` `_get_read_conn` 回退路径不持锁**（真 bug）：except 分支 docstring 声称"仍在 RLock 保护下"实际无锁——多线程并发用同一连接会 native 崩。新增 `_read_locked(fn)`：回退为写连接时强制持写锁；`fetchall/fetchone/fetch_df` 改走它。单测验证回退路径 max concurrent execute = 1。
2. **`requirements.txt` pin `duckdb==1.5.6`**：`>=0.9.0` 是雷（版本漂移），升级本身不修复事故但消除变量。
3. **compose 保留 `PYTHONFAULTHANDLER=1`**：诊断利器，段错误时有全线程栈。
4. **`market_service.py` 注释归因更正**：`_save_sw_sector_snapshot` 改 executemany 的注释原误判为"写入形态问题"，已改为正确归因（表损坏，已重建修复）。
5. **DB 升级前备份**：`/home/sos/backups/qt_pre_duckdb156.duckdb`（42MB）+ `.wal`（duckdb 格式只升不降的后路）。

## 七、遗留风险

- **WAL 自动 checkpoint 观察**：崩溃期间 WAL 涨到 10.4MB，duckdb 默认阈值 16MB。修复后旧损坏块已释放、checkpoint 路径已恢复正常，但若 WAL 再次接近阈值需关注自动 checkpoint 是否顺利（监控 WAL 文件大小即可）。
- 表损坏的**起因未明**（存储块级损坏无日志可循）。可能方向：宿主机磁盘/文件系统层。建议纳入服务器巡检（df/inode/`docker logs` 关注 `IO Error`）。

## 八、方法论沉淀（可复用）

1. **native 崩溃（无 traceback）第一动作**：`PYTHONFAULTHANDLER=1` + 段错误时全线程 dump，认 `Current thread` 行而非"第一个线程"。
2. **必现崩溃用端点二分 + RestartCount 轮询**定位触发端点；注意该 docker 版本 `{{.State.RestartCount}}` 不可用。
3. **本地无法复现时，把生产库文件 cp 进容器跑写探针**——同 OS/duckdb/文件下分离"库文件状态"变量，这是确诊表级损坏的决定性手段。
4. **stdout 块缓冲陷阱**：容器内 python print 崩溃时缓冲全丢，"无日志"≠"没在跑"——曾据此误判"零请求也崩"。
5. **生产环境修复函数内绝不放 FORCE CHECKPOINT**：WAL 有残留条目时是 hang 不是 throw。
6. **信号容器内 root 进程**：只有 `docker exec python -c "import os,signal; os.kill(pid, signal.SIGABRT)"` 可行。
