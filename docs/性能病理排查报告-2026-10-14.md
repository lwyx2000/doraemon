# DuckDB 写路径性能病理排查报告（2026-10-14）

> 缘起：longterm_service 的「参数化插入 20-55ms/行 → 字面量多行 VALUES 0.1-0.4ms/行」
> 修复（152×）获用户确认后，按指示全项目排查同类「静默付税」写路径。
> 本文全部结论有代码位置 + 本地实测（duckdb 1.5.6，与线上同代）+ 线上 job 面板数据支撑。

## 一、实测基准（本地 duckdb 1.5.6，3677 行规模，与线上 fund_rank 实际返回数一致）

|---|---|---|---|

| B 循环 参数化 INSERT ON CONFLICT | `dividend_service._pe_save_rows` | 49.7s / 3660 行 | **13.56 ms** |

| D 字面量多行 VALUES（batch 200） | `longterm_service._bulk_insert`（已修复形态） | 0.35s / 3660 行 | **0.10 ms** |

**加速比：A→D 261×，B→D 141×，C→D 168×。**

## 三、问题清单（按危害排序）

### P0-1 `etf_subscription_service._snapshot_daily`（L100-110）—— 每天 8.2 分钟
- 形态：对 fund_rank 返回的 **3677 只 ETF 逐只** DELETE + 参数化 INSERT（形态 A）
- 线上实测单次 492s；本地实测写循环本身 91s（线上文件库+容器 IO 更慢）
- 修复后预计：**~1-2s**（其余为上游取数）
- 频次：每天 19:00 + 每次容器重启补快照 → **全年白烧 ~50 小时**

### P0-2 `fund_extra_metrics_service._build_sw_industry_map`（L451-456）—— 全市场股票逐行写
- 形态：对 ~5400 只 A 股逐只 DELETE + 参数化 INSERT（形态 A）
- 估算 5400 × 2 × 25ms ≈ **3.7-4.5 分钟/次**
- 触发：进程内缓存 30 天 TTL 过期、或表为空时重建（首次/缓存失效）
- 修复后预计：**~2s**

### P1-1 `dividend_service._pe_save_rows`（L651-667）—— PE 全量回填
- 形态：逐行参数化 INSERT ON CONFLICT DO UPDATE（形态 B）
- 规模：44 指数 × ~2613 天（window_days 实测值）≈ **11.5 万行**
- 估算 11.5 万 × 13.6ms ≈ **26 分钟**（回填期一次性，摊在每天 6 指数上）
- 日常增量每次只有几行（面板 0ms），痛的是一次性全量

### P1-2 `fund_holdings_service._persist`（L233-239）—— 持仓每日补全
- 形态：executemany 参数化（形态 C）
- 规模：591 基金 × 40-115 行；每天 120 只 ≈ 9000 行 ≈ **2.4 分钟/天**（异步线程，面板不可见）
- 修复后预计：**~2s/天**

### 已核查无问题（防线良好，不需动）
- 读路径全部批量分块：`get_fee_map`/`get_map`/`attach_subscription`/`_benchmarks_in_db` 均 300-400/ chunk IN 查询，无 N+1

- `jobs/registry.py`：SQLite，非 DuckDB

## 四、修复方案（统一模式，待批准）

1. **提取公共工具**：把 `longterm_service._bulk_insert`（字面量多行 VALUES + `_sql_literal`）上移为
   `database/bulk.py`（或 `utils/db_bulk.py`），longterm_service 改为 import 复用（行为不变）。
2. **逐点替换**（按 P0→P2 顺序）：
   - `_snapshot_daily`：收集 rows 后单次批量 INSERT；DELETE 改 `WHERE trade_date = ?` 一次删当天
     （或依赖 PK 冲突用 `INSERT ... ON CONFLICT DO UPDATE`，省掉 DELETE）
   - `_build_sw_industry_map`：pairs 收集后批量 INSERT，DELETE 改 `WHERE fetched_at < now` 一次删
   - `_pe_save_rows`：ON CONFLICT 形态已在 `_bulk_insert` 支持范围内（后缀原样保留），直接换
   - `_persist` / `_ensure_fund_nav` / sw backfill ×2 / fear_greed recompute：executemany → `_bulk_insert`
   - 三个 `_upsert` / `_dy_save_one` / `_save`：单行写入改字面量单行 VALUES（去掉参数化开销即可，
     或保留参数化——单行 13-25ms 在低频路径可接受，建议一并换，统一形态）
3. **验证**：每处修后跑对应 job（etf_subscription 可手动触发），对比面板耗时；
   `_bulk_insert` 已有 longterm 全链路验证先例（三层 md5 + 13.8s 冒烟）。
4. **风险控制**：`_sql_literal` 的转义（`'` → `''`、NaN/inf → NULL）已在生产验证过；
   所有替换保持同一事务语义（原代码本就在同一连接顺序执行，无显式事务边界）。
   注意 ON CONFLICT 后缀必须原样拼回（`_bulk_insert` 的 partition 逻辑已处理）。

## 五、结论

- 病理与已获好评的修复**完全同类**：DuckDB 1.5.x 参数化绑定慢路径（13-25ms/行），
  全项目共 **11 处**写点仍在慢路径上，其中 2 处 P0（每天/每次缓存失效都白烧分钟级）。
- 修复模式成熟（`_bulk_insert` 生产验证过），预估总收益：日常每天省 ~6-10 分钟纯写库时间，
  一次性回填类省 ~30-80 分钟。
- **待用户批准后执行**（涉及核心业务写路径，按协作边界先提案）。

## 六、执行记录（2026-10-14/15，用户已批准「启动」）

**已修复并部署 53**（顺序：公共模块 → P0×2 → P1×2 → P2 批次 → 验证）：

**新实测发现的两条铁律**（已写入项目记忆与 skill）：
- DuckDB 对 aware datetime 参数化 / 带 `+08:00` 偏移字符串**均保留墙上时间**（不转 UTC）；TIMESTAMP 列字面量必须传 `_now_cst().replace(tzinfo=None)`，传 naive-UTC 会差 8 小时。
- `ON CONFLICT DO UPDATE` 同语句重复键不报错但**保留首个**；原循环「后写覆盖」语义须先 `dict` 去重。

**验证**：compileall 全树 + 10 模块 import + **41 项功能回归全过**（真实 duckdb `:memory:`，覆盖 10 处写路径：幂等/冲突 upsert/去重/naive 时间/COALESCE 后缀/边界）；9 文件 scp+md5 双验 → `compose build backend`（18s）→ force-recreate → **三层 md5 全一致** → 启动补快照 3677 只跑通 → `/api/v1/etf/` 3677/3677 有数据 → 页面全 200 → 日志零异常。

**面板耗时对比（etf_subscription_daily）**：
- 修复前（旧代码）：2026-10-14 19:00 CST 定时轮 = **492,239ms**（registry 时间戳为容器本地 UTC，`last_run=2026-10-14 11:00:00` 即该次）。
- 修复后（新代码）：部署完成于 2026-10-15 00:46 CST，当晚 19:00 定时轮自动记录；启动补快照路径已实测跑通 3677 只（写部分本地基准 ~0.4s）。
